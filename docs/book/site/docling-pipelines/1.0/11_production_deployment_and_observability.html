1. Production Deployment and Observability

This chapter covers job statistics storage backends, distributed execution with Prefect, OpenTelemetry tracing, OpenShift deployment, and OAuth2/OIDC authentication.

1.1. Job Stats Storage Backends

Docling-pipelines persists job run state, node metadata, and micro-batch progress in a configurable backend. Choose the backend that matches your environment.

Backend Env var value Best for

In-memory

memory

Tests and development; no persistence.

Filesystem (JSON)

filesystem

Single-host deployments; easy to inspect.

DuckDB

duckdb

Local development with SQL querying; no server required.

PostgreSQL

postgres

Production; multi-worker concurrent access; durable.

1.1.1. Selecting a Backend

Set DOCPIPE_STORAGE_BACKEND before starting the process:

# DuckDB (default)
export DOCPIPE_STORAGE_BACKEND=duckdb
export DOCPIPE_JOB_STATS_BASE_DIR=./data/job_stats

# PostgreSQL
export DOCPIPE_STORAGE_BACKEND=postgres
export DOCPIPE_POSTGRES_HOST=db.example.com
export DOCPIPE_POSTGRES_PORT=5432
export DOCPIPE_POSTGRES_DB=docpipe
export DOCPIPE_POSTGRES_USER=docpipe_user
export DOCPIPE_POSTGRES_PASSWORD=${DB_PASSWORD}

1.1.2. DuckDB Notes

  • Default backend for local development.

  • All data in a single file at DOCPIPE_JOB_STATS_BASE_DIR (default: data/duckdb/job_stats.duckdb).

  • Not recommended for distributed execution — use PostgreSQL instead.

1.1.3. PostgreSQL Notes

  • Required when multiple Prefect workers update job stats concurrently.

  • Workers do not need to share a filesystem.

  • Connection parameters can also be set in docling-pipelines-config.yaml.

1.2. Incremental Metadata Storage

Incremental metadata tracks which documents were processed in previous runs. Configure the backend in docling-pipelines-config.yaml:

incremental_metadata:
  storage:
    type: "filesystem"      # json | parquet | filesystem | postgresql
    config:
      base_dir: "./data/incremental_metadata"
      lock_timeout: 30.0

For PostgreSQL:

incremental_metadata:
  storage:
    type: "postgresql"
    config:
      base_dir: "./data"
      lock_timeout: 30.0
  postgres:
    host: "${INCR_META_DB_HOST:-localhost}"
    port: "${INCR_META_DB_PORT:-5432}"
    database: "${INCR_META_DB_NAME:-docpipe}"
    user: "${INCR_META_DB_USER:-docpipe_user}"
    password: "${INCR_META_DB_PASSWORD}"
    schema: "${INCR_META_DB_SCHEMA:-incremental_metadata}"

Use ${VAR:-default} for optional values with safe defaults. Never commit credentials.

1.3. Distributed Execution with Prefect

1.3.1. Execution Modes

Mode Description

Ephemeral (default)

Prefect runs in-memory. No external server needed. Suitable for development and workloads under ~1000 documents.

Server mode

Connects to a running Prefect server. Enables distributed work pools, workers, and the Prefect UI. Required for multi-machine processing.

1.3.2. Zero-Setup Ephemeral Mode

The default — no configuration needed:

docling-pipelines --flow-file my_flow.json

1.3.3. Setting Up Server Mode

# 1. Start Prefect server
prefect server start

# 2. Create a work pool
prefect work-pool create my-pool --type process

# 3. Start a worker
prefect worker start --pool my-pool

# 4. Configure environment
export PREFECT_MODE=server
export PREFECT_API_URL=http://localhost:4200/api

Add Prefect configuration to global_config:

{
  "global_config": {
    "prefect": {
      "work_pool_name": "my-pool",
      "deployment_name": "my-deployment"
    }
  }
}

1.3.4. Batch Storage Configuration

In distributed mode, micro-batches must be serialised so that workers can access them. Choose between inline (small datasets) and filesystem/S3 (large datasets):

{
  "global_config": {
    "prefect": {
      "work_pool_name": "my-pool"
    },
    "batch_storage": {
      "type": "local",
      "path": "/shared/batches"
    }
  }
}

For S3:

{
  "batch_storage": {
    "type": "s3",
    "path": "s3://my-bucket/batches"
  }
}
For distributed workers, batch_storage.path must resolve to the same shared path on both the submitter and all worker machines.

For full Prefect configuration including Docker work pools, see docs/integrations/prefect/DISTRIBUTED_EXECUTION_GUIDE.md.

1.4. OpenTelemetry Tracing

Docling-pipelines ships built-in OpenTelemetry instrumentation for HTTP requests (automatic) and operator execution spans.

1.4.1. Quick Start with Jaeger

# Start Jaeger (all-in-one)
docker run -d --name jaeger \
  -p 16686:16686 \
  -p 4317:4317 \
  -p 4318:4318 \
  jaegertracing/all-in-one:latest

# Configure docpipe
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
export OTEL_SERVICE_NAME=docpipe
export DS_OTEL_ENABLED=true

docling-pipelines --flow-file my_flow.json

View traces at http://localhost:16686.

1.4.2. Environment Variables

Variable Default Description

DS_OTEL_ENABLED

false

Enable OpenTelemetry instrumentation.

OTEL_EXPORTER_OTLP_ENDPOINT

—

OTLP exporter endpoint (gRPC port 4317 or HTTP port 4318).

OTEL_SERVICE_NAME

Service name shown in traces.

OTEL_TRACES_SAMPLER

always_on

Sampling strategy: always_on, always_off, traceidratio.

OTEL_TRACES_SAMPLER_ARG

Sampling ratio (0.0–1.0) for traceidratio.

1.4.3. Supported Monitoring Backends

Backend Notes

Jaeger

Local development. All-in-one Docker image available.

Grafana Tempo (managed)

Grafana Cloud. Configure with OTLP_ENDPOINT and base64-encoded credentials.

Self-hosted. Same OTLP configuration.

Use AWS Distro for OpenTelemetry.

1.5. OpenShift Deployment

1.5.1. Prerequisites

  • oc CLI installed and logged in.

  • Permissions to create deployments and services in the target namespace.

  • Git repository accessible from the cluster (public or with credentials).

1.5.2. Quick Deployment

git clone https://github.com/IBM/docling-pipelines.git
cd docling-pipelines

# Deploy to OpenShift
bash scripts/deploy_openshift.sh \
  --project my-docpipe-project \
  --app-name docpipe-api

# Monitor deployment
oc rollout status deployment/docpipe-api -n my-docpipe-project

# Get the route URL
oc get route docpipe-api -n my-docpipe-project

1.5.3. Environment Variables on OpenShift

oc set env deployment/docpipe-api \
  DS_LOG_LEVEL=INFO \
  DOCPIPE_STORAGE_BACKEND=postgres \
  DOCPIPE_POSTGRES_HOST=postgresql.svc.cluster.local \
  CORS_ORIGINS=https://my-frontend.apps.cluster.example.com \
  -n my-docpipe-project

1.5.4. Resource Limits

resources:
  requests:
    cpu: "500m"
    memory: "1Gi"
  limits:
    cpu: "2000m"
    memory: "4Gi"

1.5.5. Scaling

# Scale to 3 replicas
oc scale deployment/docpipe-api --replicas=3 -n my-docpipe-project

# Auto-scaling
oc autoscale deployment/docpipe-api \
  --min=2 --max=10 --cpu-percent=70 \
  -n my-docpipe-project

For the full OpenShift guide including BuildConfig, ImageStream, persistent storage, CI/CD webhooks, and troubleshooting, see docs/deployment/OPENSHIFT.md.

1.6. OAuth2 / OIDC Authentication

The REST API supports two authentication paths:

Path Mechanism Use when

LDAP

POST /auth/login with username/password.

Internal deployments with an LDAP directory.

OAuth2 / OIDC

Authorization Code flow with PKCE.

SSO providers: Google, Azure AD, Okta, Keycloak.

Both paths produce a short-lived JWT passed as Authorization: Bearer <token>.

1.6.1. Configuring OAuth2

# Google
OAUTH2_ENABLED=true
OAUTH2_PROVIDER=google
OAUTH2_CLIENT_ID=your-client-id.apps.googleusercontent.com
OAUTH2_CLIENT_SECRET=${OAUTH2_CLIENT_SECRET}
OAUTH2_REDIRECT_URI=https://your-domain.com/auth/oauth2/callback
JWT_SECRET_KEY=${JWT_SECRET_KEY}

# Azure AD
OAUTH2_PROVIDER=azure
AZURE_TENANT_ID=your-tenant-id
OAUTH2_CLIENT_ID=your-application-id
OAUTH2_CLIENT_SECRET=${OAUTH2_CLIENT_SECRET}

# Generic OIDC (Okta, Keycloak, Auth0, GitLab)
OAUTH2_PROVIDER=generic
OAUTH2_DISCOVERY_URL=https://your-provider.com/.well-known/openid-configuration
OIDC_ISSUER=https://your-provider.com
OIDC_AUDIENCE=your-client-id

1.6.2. OAuth2 Flow

1. Client → GET /auth/oauth2/authorize?provider=google
2. Server → Redirect to OAuth2 provider
3. User authenticates with provider
4. Provider → Redirect to /auth/oauth2/callback?code=xxx&state=xxx
5. Server exchanges code for tokens, validates ID token
6. Server creates JWT and returns it to the client
7. Client uses JWT for all subsequent API requests

1.6.3. Security Best Practices

  • Always use HTTPS in production. Set OAUTH2_REDIRECT_URI to an https:// URL.

  • Use a strong, random JWT_SECRET_KEY: python -c "import secrets; print(secrets.token_urlsafe(32))"

  • Set JWT_ACCESS_TOKEN_EXPIRE_MINUTES and OAUTH2_SESSION_EXPIRE_MINUTES to short values appropriate for your security policy.

  • Restrict CORS_ORIGINS to your frontend domain only.

  • For production state storage, use Redis instead of in-memory state.

For the complete OAuth2/OIDC configuration guide, see docs/api/OAUTH2_AUTHENTICATION.md.

1.7. Security Hardening

The REST server applies several hardening measures out of the box:

  • Security headers — X-Content-Type-Options, X-Frame-Options, Content-Security-Policy, and Referrer-Policy on every response.

  • Payload size limit — POST/PUT/PATCH requests exceeding 5 MB are rejected (HTTP 413).

  • ACL enforcement — document endpoints filter by allowed_users at query time; unauthorised resources return 404 (not 403) to prevent information leakage.

  • JWT validation — short-lived tokens validated on every protected request.

Additional production hardening:

  • Terminate TLS at a reverse proxy (nginx, HAProxy) — never expose the uvicorn process directly.

  • Set DOCPIPE_POSTGRES_* for a durable job stats backend.

  • Use HashiCorp Vault for secrets — see docs/integrations/vault/README.md.

  • Enable audit logging via the telemetry stack (OTEL + Jaeger/Grafana).

1.8. Monitoring and Alerting

Key metrics to monitor in production:

Metric Alert threshold

Job run failure rate

Alert when >5% of runs in any 1-hour window fail.

Operator failed_docs_count

Alert when any operator reports >10% failed documents.

API error rate (5xx)

Alert when >1% of API requests return 5xx.

OpenSearch cluster health

Alert on red cluster status.

Queue depth (Prefect)

Alert when work pool queue exceeds 100 pending flows.
