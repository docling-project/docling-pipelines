# Spec Delta

## Purpose

The safety and execution contract for SQL generated by an LLM and run against entity tables written by `EntityStoreOperator`. The generated statement is untrusted input. This capability defines what may be executed, how the engines are locked down, which limits apply, and what is never logged. Engines are reached only through `SqlEnginePort`; first release adapters are DuckDB and Postgres. Behavior that mirrors the hardened SQL path of retrieval-v2 (scope-aware authorization, safe engine diagnostics, deadlines, cancellation) is adopted here on docpipe's engines.

## ADDED Requirements

### Requirement: Single read-only SELECT
The validator SHALL parse generated SQL with `sqlglot` in the engine's dialect and SHALL accept it only if it is exactly one statement and a `SELECT` (including CTEs and set operations of SELECTs). It MUST reject multiple statements, DDL, DML, `COPY`, `ATTACH`, `INSTALL`, `LOAD`, `PRAGMA`, `SET`, `CALL`, `EXPLAIN ANALYZE`, and any parse failure. Rejection SHALL be treated like an execution error for the retry loop.

#### Scenario: Plain select
- **WHEN** the SQL is `SELECT id, total FROM entity_orders WHERE total > 100`
- **THEN** it is accepted

#### Scenario: Stacked statements
- **WHEN** the SQL is `SELECT 1; DROP TABLE entity_orders`
- **THEN** it is rejected before execution

#### Scenario: Data modification
- **WHEN** the SQL is `DELETE FROM entity_orders`
- **THEN** it is rejected

#### Scenario: Unparseable
- **WHEN** the SQL cannot be parsed
- **THEN** it is rejected

### Requirement: Scope-aware table authorization
One function, `validate_and_authorize`, SHALL run the read-only check and then check every physical relation found by walking the statement's scopes against the entity tables listed in the derivative for the target. It SHALL be called for every statement before the engine: each generated statement, each corrected statement, and any fixed read. CTE names are not physical tables, but the tables a CTE reads SHALL be checked.

#### Scenario: Allowed table
- **WHEN** the statement selects from `entity_orders` and `entity_orders` is in the derivative
- **THEN** it is accepted

#### Scenario: Other table
- **WHEN** the statement selects from `users`
- **THEN** it is rejected and the engine is not called

#### Scenario: CTE shadowing
- **WHEN** a CTE is named like an allowed table but reads an unauthorized table, or is named like an unauthorized table
- **THEN** the CTE name authorizes nothing and the unauthorized table it reads is rejected

#### Scenario: Denied first candidate
- **WHEN** the first generated statement reads an unauthorized table
- **THEN** the engine is not called for it, a correction is requested with the table message, and only a permitted correction is executed

### Requirement: Only plain tables and resolved names
A FROM item that is not a plain table (table function, four-part name, subquery-generated relation such as `generate_series` or `read_csv`) SHALL be rejected. System catalogs (`information_schema`, `pg_catalog`, `duckdb_*`, `pragma_*`) SHALL be rejected. A name SHALL be accepted only when it resolves to exactly one authorized `schema.table` using the session schema the engine applies.

#### Scenario: Table function
- **WHEN** the statement calls `read_csv('/etc/passwd')`, `read_text(...)`, `pg_read_file(...)` or `glob(...)`
- **THEN** it is rejected

#### Scenario: Catalog access
- **WHEN** the statement selects from `information_schema.tables` or `pg_catalog.pg_shadow`
- **THEN** it is rejected

#### Scenario: Bare name resolves to the session schema
- **WHEN** the engine session schema is the entity schema and the statement uses a bare allowed table name
- **THEN** it is accepted

#### Scenario: Name in another schema
- **WHEN** the statement qualifies an allowed table name with a different schema
- **THEN** it is rejected

#### Scenario: Identifier case
- **WHEN** the dialect folds unquoted identifiers and the statement spells an allowed table in another case
- **THEN** it is accepted, while a quoted identifier that differs in case on a case-preserving dialect is rejected

#### Scenario: Authorization is table-level
- **WHEN** a statement selects any column of an allowed table
- **THEN** no column-level grant check is claimed, and column permissions remain with the database role

### Requirement: Id column required
The statement SHALL select the `id` column of at least one allowed table, directly or through an alias, so rows can be correlated. A statement without it SHALL be rejected with an error message that the retry loop passes to the model; aggregate-only queries (`COUNT`, `SUM` without `id`) MAY be accepted and returned without `document_id`.

#### Scenario: Missing id on row query
- **WHEN** a non-aggregate statement does not select `id`
- **THEN** it is rejected with a correction message

#### Scenario: Aggregate query
- **WHEN** the statement is `SELECT COUNT(*) FROM entity_orders`
- **THEN** it is accepted and its rows have no `document_id`

### Requirement: DuckDB hardening
The DuckDB adapter SHALL open the database file read-only, then execute `SET enable_external_access=false` and `SET lock_configuration=true` before any generated statement. It MUST NOT reuse the pipeline's read-write connection or `DuckDBConnectionManager` singleton. If the file cannot be opened read-only (for example, a pipeline holds it read-write), the store SHALL be reported failed with reason `store_busy`. The adapter SHALL enforce the timeout and cancellation with `connection.interrupt()`.

#### Scenario: External access blocked
- **WHEN** a statement that slipped past validation calls `read_text('/etc/passwd')`
- **THEN** the engine raises and no file content is returned

#### Scenario: Configuration locked
- **WHEN** a statement tries `SET enable_external_access=true`
- **THEN** it fails

#### Scenario: Database busy
- **WHEN** another process holds the file read-write
- **THEN** the store is reported failed with reason `store_busy` and other stores are still returned

### Requirement: Postgres hardening
The Postgres adapter SHALL connect with a role that has `SELECT` only on the entity schema, run each statement in a read-only transaction, set `statement_timeout` to `retrieval.sql.timeout_seconds`, set `search_path` to the entity schema only, and roll back after each query.

The retrieval connection SHALL be configured separately from the pipeline's write credentials, using `DOCPIPE_RETRIEVAL_POSTGRES_*` and falling back to `DOCPIPE_POSTGRES_*` with a startup warning.

#### Scenario: Write attempt
- **WHEN** a statement that slipped past validation attempts `INSERT`
- **THEN** Postgres rejects it because the transaction is read-only

#### Scenario: Timeout
- **WHEN** a query exceeds `retrieval.sql.timeout_seconds`
- **THEN** it is cancelled and the SQL store is reported failed with reason `timeout`

#### Scenario: Fallback credentials warning
- **WHEN** no dedicated retrieval Postgres credentials are set
- **THEN** a startup warning states that write-capable credentials are used

### Requirement: Row cap and timeout enforced in the engine
The engine SHALL return at most `min(limit, retrieval.sql.max_rows)` rows, enforced by wrapping or limiting the statement and by truncating fetched rows, and SHALL enforce the effective statement timeout (see "Deadline travels to the engine") independent of the model-generated SQL. A statement's own `LIMIT` larger than the cap SHALL be reduced.

#### Scenario: Large result
- **WHEN** a statement matches 10,000 rows and the cap is 100
- **THEN** 100 rows are returned and `metadata.row_count` is 100

#### Scenario: Model sets huge limit
- **WHEN** the statement has `LIMIT 1000000`
- **THEN** the effective limit is the cap

### Requirement: Prompt grounding and schema exposure
The text-to-SQL prompt SHALL contain only the allowed tables and their column names and types, the dialect, the id-column rule, and the user question delimited as data. It MUST NOT contain connection details, file paths, or row data. Column names and types come from the engine's catalog for the allowed tables only.

#### Scenario: Prompt content
- **WHEN** a prompt is built for two allowed tables
- **THEN** it lists only those two tables' columns and no path or credential

### Requirement: Logging and error hygiene for SQL
Generated SQL, bound values, and fetched rows MUST NOT be logged at INFO or above and MUST NOT be present in client error messages or events. Logs MAY include attempt number, duration, row count, error category, and a hash of the SQL. `metadata.sql` in a response is allowed only when the caller sets `include_sql`.

#### Scenario: Failed statement
- **WHEN** a statement fails at the database
- **THEN** the log contains the error category and SQL hash, and the client sees a generic reason

### Requirement: Engine abstraction
`SqlEnginePort` SHALL expose `dialect`, `capabilities`, `describe_tables(*, tables)`, and `execute(*, sql, max_rows, timeout_seconds, cancel)` and SHALL be the only way the retrieval engine runs SQL. Operators and the retrieval application layer MUST NOT call `TableStoragePort.execute_query` or database drivers directly.

#### Scenario: Swapping engines
- **WHEN** a Presto adapter implementing `SqlEnginePort` is registered later
- **THEN** the orchestration and validation code needs no change beyond the dialect and capabilities

### Requirement: Engine capabilities are declared
Each engine SHALL declare `capabilities` with `statement_timeout`, `read_only_session`, and `cancellation`, each naming the mechanism or null. The service SHALL NOT claim enforcement the engine does not declare, and SHALL log once per statement that an undeclared limit is not enforced on the server.

#### Scenario: DuckDB
- **WHEN** the DuckDB engine reports its capabilities
- **THEN** `read_only_session` names the read-only open, `statement_timeout` names the interrupt timer, and `cancellation` names `interrupt`

#### Scenario: Postgres
- **WHEN** the Postgres engine reports its capabilities
- **THEN** it names `statement_timeout`, a read-only transaction, and `connection.cancel`

#### Scenario: Engine without a read-only session
- **WHEN** a later engine declares no read-only session
- **THEN** the validator is documented as the only read-only guard for it

### Requirement: Deadline travels to the engine
The request deadline SHALL be an absolute monotonic instant carried from the search request to every statement. Each statement SHALL receive the time left, rounded up to whole milliseconds and never zero, as its server-side limit, capped by `retrieval.sql.timeout_seconds`. When the deadline has passed, no engine call and no correction call SHALL be made, and the result SHALL carry a `timeout_error` diagnostic.

#### Scenario: Sub-millisecond budget
- **WHEN** the time left is positive but under one millisecond
- **THEN** the limit sent is 1 ms, never 0

#### Scenario: Deadline passed
- **WHEN** a statement is about to run after the deadline
- **THEN** the engine and the text-to-SQL service are not called and the store is reported failed with reason `timeout`

#### Scenario: Cap applies
- **WHEN** the time left exceeds `retrieval.sql.timeout_seconds`
- **THEN** the limit sent is `retrieval.sql.timeout_seconds`

### Requirement: Cancelling a wait cancels the statement
When the wait for a statement is abandoned (per-store timeout, request deadline, shutdown), the service SHALL ask the engine to stop that statement through a handle scoped to that statement, and SHALL record the outcome as `acknowledged`, `unconfirmed`, or `not_running`. Rows read after a cancel SHALL be discarded and a `cancelled` diagnostic raised.

#### Scenario: DuckDB cancel
- **WHEN** a DuckDB statement is running and its wait is abandoned
- **THEN** the connection is interrupted, the outcome is acknowledged when the statement ends with the interrupt error, and no rows are returned

#### Scenario: Postgres cancel
- **WHEN** a Postgres statement is running and its wait is abandoned
- **THEN** a cancel request is sent on that statement's connection and the outcome is acknowledged only when the server reports the statement as canceled

#### Scenario: Unconfirmed
- **WHEN** the engine has no cancel mechanism or the request could not be sent
- **THEN** the outcome is `unconfirmed` and a warning is logged

#### Scenario: Already finished
- **WHEN** a cancel arrives after the statement ended and its connection was closed
- **THEN** no engine call is made and the outcome is `not_running`

#### Scenario: Statement-scoped handles
- **WHEN** two statements run concurrently and one wait is abandoned
- **THEN** only that statement receives a cancel request

### Requirement: Safe engine diagnostics
Each engine adapter SHALL convert a driver failure at its own boundary into a diagnostic with a fixed message template, the engine code, and a kind such as `syntax_error`, `column_not_found`, `table_not_found`, `type_mismatch`, `authorization_error`, `timeout_error`, `cancelled`, or `connection_error`. Raw driver text MUST NOT reach the correction prompt, logs, error context, or client, and the raw exception MUST NOT remain on the cause chain.

#### Scenario: Secrets in a driver exception
- **WHEN** a driver exception contains a DSN, token, host, or file path
- **THEN** the correction prompt, log records, error message, error context, and formatted traceback contain none of them

#### Scenario: Identifier kept only if submitted
- **WHEN** the engine names a missing column
- **THEN** the diagnostic keeps the kind and engine code, and names the identifier only if it appears in the submitted SQL

#### Scenario: Type mismatch under a generic code
- **WHEN** the engine reports a date compared with a text literal under a generic syntax error code
- **THEN** the diagnostic kind is `type_mismatch` with SQL type names only

### Requirement: Non-repairable failures are not corrected
The service SHALL request a corrected statement only for diagnostic kinds a new statement can fix (syntax, missing column, table or function, type, aggregation, and validator rejection). Connection, authorization, rate-limit, timeout, and cancelled failures SHALL be returned as the store's failure without a correction call.

#### Scenario: Authorization failure
- **WHEN** a generated statement fails with `authorization_error`
- **THEN** no correction call is made and the store is reported failed with reason `authorization_error`

#### Scenario: Missing column is repairable
- **WHEN** a statement fails with `column_not_found`
- **THEN** the correction prompt receives the kind and the real column names of the referenced allowed tables, and no raw engine text
