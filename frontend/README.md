# Docling Pipelines Frontend

> **⚠️ Beta notice:** The Docling Pipelines web UI is **experimental and not yet production-ready**. APIs, UI structure, and features may change without notice between releases. For production workloads, use the CLI, Python API (`DocpipeFlowManager`), or REST API instead.

A React + TypeScript frontend application built with Vite and IBM Carbon Design System for the Docling Pipelines project.

## Prerequisites

Before running this application, ensure you have the following installed:

- **Node.js** (version 22.15.1 - specified in `.nvmrc`)
- **npm** (comes with Node.js) or **yarn**
- **nvm** (Node Version Manager) - recommended for managing Node.js versions
- **TypeScript** knowledge - This project uses TypeScript for type safety

## Getting Started

### 1. Set Node Version

If you have nvm installed, use the correct Node.js version:

```bash
cd frontend
nvm use
```

This will automatically use Node.js 22.15.1 as specified in the `.nvmrc` file.

### 2. Install Dependencies

Install the required dependencies including Carbon Design System:

```bash
npm install
```

Or if you prefer yarn:

```bash
yarn install
```

### 3. Run Development Server

Start the development server with hot module replacement (HMR):

```bash
npm run dev
```

Or with yarn:

```bash
yarn dev
```

The application will automatically open in your browser at `http://localhost:3000`.

### 4. Build for Production

To create an optimized production build:

```bash
npm run build
```

Or with yarn:

```bash
yarn build
```

The built files will be generated in the `dist/` directory.

### 5. Preview Production Build

To preview the production build locally:

```bash
npm run preview
```

Or with yarn:

```bash
yarn preview
```

## BFF Architecture

This application uses a **Backend for Frontend (BFF)** pattern to separate concerns and provide a clean API layer.

### Architecture Overview

```
React App (Port 3000)
    ↓ Vite Proxy (/api/*)
BFF Server (Port 3001)
    ↓ HTTP Proxy
Python Backend (Port 8000)
```

### Why BFF?

1. **Separation of Concerns**: Frontend logic stays in React, backend logic in Python
2. **API Aggregation**: BFF can combine multiple backend calls into one frontend call
3. **Security**: Sensitive operations and credentials stay on the server side
4. **Flexibility**: Easy to add caching, rate limiting, or request transformation

### BFF Components

#### 1. Frontend Actions (`src/services/api/actions/`)
HTTP calls to BFF endpoints using axios. These are simple, focused functions:

```typescript
// src/services/api/actions/operator-actions.ts
export const getOperatorMetadata = async (): Promise<AxiosResponse<OperatorsResponse>> => {
  const url = '/api/fetchOperatorMetadata';  // Proxied to BFF by Vite
  return await axios.get<OperatorsResponse>(url);
};
```

#### 2. BFF Controllers (`server/controllers/`)
Express.js controllers that proxy requests to the Python backend:

```javascript
// server/controllers/operator-controller.js
const fetchOperatorMetadata = async (req, res) => {
  const backendUrl = `${BACKEND_API_URL}/api/v1/operators/metadata`;
  const response = await axios.get(backendUrl);
  res.json(response.data);
};
```

#### 3. Vite Proxy Configuration
Vite dev server proxies `/api/*` requests to BFF:

```typescript
// vite.config.ts
server: {
  proxy: {
    '/api': {
      target: 'http://localhost:3001',  // BFF server
      changeOrigin: true,
    }
  }
}
```

### Request Flow

1. **React Component** calls action: `getOperatorMetadata()`
2. **Axios** makes request to `/api/fetchOperatorMetadata`
3. **Vite Proxy** forwards to `http://localhost:3001/api/fetchOperatorMetadata`
4. **BFF Controller** proxies to Python backend: `http://localhost:8000/api/v1/operators/metadata`
5. **Python Backend** processes request and returns data
6. **BFF** forwards response to React
7. **React Component** receives data and updates UI

### Running the BFF

The BFF server runs alongside the Vite dev server:

```bash
# Start both servers with one command
npm run dev

# Or start separately for debugging
npm run dev:bff   # BFF server on port 3001
npm run dev:vite  # Vite dev server on port 3000
```

### Environment Variables

BFF configuration in `server/.env` (copy from `frontend/.env.example`):

```env
BACKEND_API_URL=http://localhost:8080
BFF_PORT=3001
```

### Adding New BFF Endpoints

1. **Create action** in `src/services/api/actions/`:
   ```typescript
   export const getFlows = async () => {
     return await axios.get('/api/flows');
   };
   ```

2. **Create controller** in `server/controllers/`:
   ```javascript
   const getFlows = async (req, res) => {
     const response = await axios.get(`${BACKEND_API_URL}/api/v1/flows`);
     res.json(response.data);
   };
   ```

3. **Register route** in `server/server.js`:
   ```javascript
   app.get('/api/flows', flowController.getFlows);
   ```

For build integration details (wheel, Docker, CI/CD), see [`FRONTEND_BUILD_INTEGRATION.md`](../FRONTEND_BUILD_INTEGRATION.md).

## Troubleshooting

### Port Already in Use

If port 3000 is already in use, you can change it in `vite.config.js`:

```javascript
export default defineConfig({
  plugins: [react()],
  server: {
    port: 3001, // Change to your preferred port
    open: true
  }
})
```

### Module Not Found Errors

If you encounter module not found errors, try:

```bash
rm -rf node_modules package-lock.json
npm install
```

### SCSS Compilation Issues

If you encounter SCSS compilation errors with Carbon styles, ensure you have the latest version of Vite and the React plugin:

```bash
npm update @vitejs/plugin-react vite
```

### Node Version Mismatch

If you're using a different Node.js version, switch to the correct version:

```bash
nvm install 22.15.1
nvm use 22.15.1
```

## Building the Wheel (with Frontend Assets)

The React frontend can be bundled into the Python wheel package so it is served directly by the FastAPI backend after installation.

### Prerequisites

- Node.js 22.15.1+ and npm (optional, but recommended)
- If Node.js is not available, the build will continue without frontend assets

### Build Steps

From the **project root**:

```bash
uv build --wheel
```

**What happens during build:**
1. Hatch build hook executes `scripts/build_frontend.py`
2. Frontend is built with Vite (if npm is available)
3. Built assets are copied to `src/docpipe/api/static/`
4. Wheel package includes frontend assets
5. After installation, UI is accessible at `http://localhost:8080/ui`

### Build Without Frontend

If Node.js is not installed, the build skips the frontend and creates a wheel with only the backend:

```bash
uv build --wheel
# Warning: npm not found. Skipping frontend build.
```

For detailed frontend build integration documentation, see [`FRONTEND_BUILD_INTEGRATION.md`](../FRONTEND_BUILD_INTEGRATION.md).

The wheel file will be created in the `dist/` directory.

## Internationalization (i18n)

All user-visible strings are externalised via [react-intl](https://formatjs.io/docs/react-intl/).

### How it works

The app root (`main.tsx`) is wrapped in `<IntlProvider>` which supplies the active locale and its
message map. Message maps live in `src/i18n/messages_<locale>.json` and are loaded dynamically at startup via `src/i18n/index.ts`. Only the required locale file is downloaded by the client.

### Strings outside the translation catalog

Text served by the backend is not part of the react-intl catalog and is shown as received
(English only). This includes the operator metadata `description` fields used for field
tooltips, operator labels and valid-value lists.

### Adding strings to a component

Every component that contains user-visible text must have a companion `<ComponentName>.messages.ts`
file in the **same directory**. Strings are never hardcoded inline.

```
src/components/cards/
  FlowsCard.tsx
  FlowsCard.messages.ts   <- descriptor file
```

**`FlowsCard.messages.ts`**

```typescript
import { defineMessages } from 'react-intl';

export const messages = defineMessages({
  title: {
    id: 'src.components.cards.FlowsCard.title',
    defaultMessage: 'Flows',
  },
  emptyTitle: {
    id: 'src.components.cards.FlowsCard.emptyTitle',
    defaultMessage: 'No recent flows',
  },
});
```

**`FlowsCard.tsx`** — consume with `useIntl`:

```typescript
import { useIntl } from 'react-intl';
import { messages } from './FlowsCard.messages';

export function FlowsCard() {
  const intl = useIntl();
  return (
    <HomeCard title={intl.formatMessage(messages.title)} />
  );
}
```

### ID naming convention

IDs follow the file path relative to `frontend/`, using dots as separators, ending with the element name.
When the filename repeats the parent folder name (e.g. `Home/Home.tsx`, `DeleteModal/DeleteModal.tsx`),
the filename segment is dropped. The folder already provides the namespace.

```
src.components.cards.FlowsCard.title
src.components.cards.FlowsCard.emptyTitle
src.pages.Home.heading
src.components.common.DeleteModal.confirmButton
```

### Generating / updating `messages_en.json`

Run the extractor after adding or changing any descriptor:

```bash
npm run extract:messages
```

This scans all `*.ts` / `*.tsx` files and writes every `id` + `defaultMessage` pair into
`src/i18n/messages_en.json`. **Never edit `messages_en.json` by hand**. It is fully owned by the extractor.

### Adding a new locale

When a translation workflow is in place:

1. Translate the values (keep the keys unchanged) through the workflow.
2. Place the translated file at `src/i18n/messages_<locale>.json`. The loader picks it up automatically via dynamic import, no changes to `index.ts` needed.
3. Add the locale code to `SUPPORTED_LOCALES` in `src/main.tsx`.

### CI lint enforcement

`eslint-plugin-formatjs` is configured in `eslint.config.js` and will throw an error if:
- A `defineMessages` descriptor is missing `defaultMessage`
- An ID uses camelCase instead of dot-separated form
